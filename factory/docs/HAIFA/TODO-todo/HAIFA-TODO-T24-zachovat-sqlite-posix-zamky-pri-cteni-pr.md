# Přehled zachovává SQLite POSIX zámky

Diagnostika T23 v [main CI 39524730103](https://github.com/janbkrejci/HAIFA/actions/runs/39524730103), přečtená z `/tmp/haifa-main-v2-failure.log`, zachytila HTTP 500 při retry z Backlogu. Odpověď obsahovala `DatabaseError: database disk image is malformed (in _ensure_wal, store.py:639)`; stejně selhal diagnostický GET `/runs`. Log retry subprocessu přitom končí úspěšně dokončeným druhým pokusem. Nejde tedy jen o odmítnutí retry nebo neúspěch jeho workflow.

Původní `_closed_wal` četl přes `db.open("rb")` dvacet bajtů hlavičky a zavíral fd v serverovém procesu, kde současně žijí SQLite spojení launcheru. [SQLite, oddíl 2.2](https://www.sqlite.org/howtocorrupt.html#_posix_advisory_locks_canceled_by_a_separate_thread_doing_close_) dokumentuje, že takové zavření zruší všechny POSIX advisory locks procesu na stejném souboru. SQLite samo spravuje zavírání svých spojení tak, aby tyto zámky zachovalo. Obrany od SQLite 3.51 nejsou úplným řešením; tato změna nevyžaduje změnu runtime verze.

Regrese tento mechanismus reprodukovala před změnou produkčního kódu: při čtecí i zapisovací WAL transakci byl konfliktní `fcntl.lockf` z jiného procesu před GET Přehledu odmítnut, ale po GET uspěl. Obě varianty tedy selhaly přesně na ztrátě zámku. Po opravě obě procházejí. Probe nic nezapisuje a běží vždy v čerstvém procesu, protože zámky jsou per-process. Po uzavření SQLite spojení navíc ověřuje uvolnění zámku. Test kontroluje data před čtením i po commitu a integritu také po novém otevření databáze. Tím je prokázána a opravena konkrétní chyba zámků; test se nesnaží náhodně vyvolat fyzickou korupci ani dokazovat, že byla jedinou možnou příčinou CI selhání.

Nový `_without_journal` používá jen `stat` sidecarů. Při existujícím `-wal`, `-shm` nebo `-journal`, i prázdném, se otevře `mode=ro`; při chybě metadat se rovněž konzervativně použije SQLite se zámky. Bez sidecarů se otevře `mode=ro&immutable=1`. Tím odpadá raw čtení hlavičky a zůstává absence nových WAL/SHM souborů při čtení uzavřené databáze. Chybějící DB se nevytvoří a všechny čtecí connection mají `query_only`.

Se současně běžícím WAL writerem čtenář používá normální SQLite synchronizaci, vidí commitnuté změny z WAL a nevidí necommitnuté změny writeru. Zavření čtecí SQLite connection zachová zámky writeru. Přenosné regrese ověřují tyto vlastnosti a zákaz zápisu také s rollback journalem. Kontrola sidecarů je pouze okamžitá indicie klidu, nikoli atomický důkaz: writer spuštěný až po této kontrole může způsobit starší výsledek daného pollu nebo varování při chybě čtení. Následující poll metadata znovu vyhodnotí. Nevzniká tím raw zavření fd, které by shodilo zámky existujícího writeru. Nejde o garantovaný atomický snapshot všech dotazů Přehledu.

HTTP retry se neopakuje kvůli maskování chyby, malformed se nepřekládá na úspěch a žádná DB ani WAL se nemaže. Diagnostika T23 a původní browser assertions zůstávají zachované.

Lokálně prošel lint, formát a mypy obou změněných Python souborů a všech 145 testů v `test_web_overview.py`, `test_web_db_busy.py`, `test_web_backlog.py`, `test_web_control.py` a `test_web_runs.py`. Obsahují původní kontrolu beze změn databáze a sidecarů i novou regresi zámků. Globální `just lint` a `just typecheck` patří povinnému testovacímu kroku workflow; builder podle svého omezení kontroluje pouze změněné soubory. Prošly také všechny tři browser scénáře: `test_retry_browser.py` (detail běhu a Backlog) a `test_multi_repo_browser.py`, s lokálním fake harness a bez živých služeb. Celá suite je ponechána CI.
